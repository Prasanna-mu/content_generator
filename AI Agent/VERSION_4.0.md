# Content Generator --- Version 4.0

## Stabilization, Quality Control, Output Reliability & Documentation

**Version:** 4.0\
**Status:** Planned\
**Scope:** Existing Content Generator pipeline only\
**Implementation approach:** Incremental, test-driven, no unnecessary
rewrite

------------------------------------------------------------------------

# 1. Version 4.0 Objective

Version 4.0 is focused on stabilizing the existing Content Generator
before adding major new capabilities.

The current implementation already has a 10-stage educational content
pipeline covering prompt analysis, optional web search, lesson
generation/refinement, subtopic generation/validation, content
generation, output writing, and DOCX export. It also has SQLite-based
session/checkpoint support and an LLM abstraction layer.

The V4 goal is to fix the known implementation bugs and improve the
quality and reliability of generated subtopics and final documents.

The primary goals are:

1.  Generate **exactly one final content file per subtopic**.
2.  Prevent excessively long or incorrect subtopic filenames.
3.  Make subtopic names **short, clear, and usable as
    filenames/headings**.
4.  Detect repeated/near-duplicate subtopics.
5.  Regenerate weak, short, repeated, or invalid subtopics
    automatically.
6.  Fix resumed-content tasklist/checkpoint inconsistencies.
7.  Make subtopic numbering independent of fragile lesson-list ordering.
8.  Remove content-generation filename mismatches.
9.  Make all normal websites available to the web-search/trusted-source
    system without an unnecessary domain allowlist, while retaining
    security protections.
10. Improve DOCX formatting so Markdown-style headings and emphasis
    become real Word headings/bold formatting rather than literal
    Markdown characters.
11. Keep the pipeline memory-efficient by persisting completed
    generation results promptly.
12. Preserve existing Ollama, web search, session/resume, quiz,
    question-bank, and DOCX functionality.

# 2. Known Bugs and Planned Adjustments

## 2.1 Duplicate File Writing

### Problem

The implementation currently has two paths capable of writing content
files:

-   The orchestrator writes a `.txt` file during content generation.
-   `OutputWriter` writes the final content file again.

This results in two files for the same subtopic.

### V4 Requirement

There must be **one authoritative final content-writing path**.

Preferred flow:

``` text
LLM Generation
    ↓
Content Validation
    ↓
Persist/checkpoint result
    ↓
OutputWriter
    ↓
ONE final TXT file
```

The orchestrator should not independently create a second final `.txt`
file.

Do not keep duplicate content files merely as intermediate storage.

# 3. Subtopic Naming

## 3.1 Short Subtopic Names

Subtopic names generated by the LLM should be short, specific, readable,
and suitable for:

-   course navigation
-   headings
-   filenames
-   DOCX sections
-   UI display

Avoid extremely long titles containing full explanations.

### Bad

``` text
Understanding the Various Methods and Techniques Used to Identify, Analyze, Validate, and Prioritize User Requirements in Complex Engineering Design Projects
```

### Better

``` text
User Requirement Analysis
```

The system should enforce a configurable maximum title length.

If an LLM generates an overly long title, the system should either:

1.  regenerate the title, or
2.  ask the LLM to shorten it,

depending on the existing generation architecture.

The preferred result is a meaningful short title rather than blind
truncation.

# 4. Content Generation Filename Mismatch

## Problem

The current implementation can construct content filenames using the
original user prompt instead of the actual subtopic title.

This creates filenames such as:

``` text
01_01_I_need_a_course_on_design_thinking_for_engineering_students_...
```

instead of:

``` text
01_01_User_Requirement_Analysis.txt
```

## V4 Requirement

Filename generation must be based on:

``` text
lesson number
+
subtopic number
+
short sanitized subtopic title
```

Example:

``` text
01_01_User_Requirement_Analysis.txt
01_02_User_Research_Methods.txt
01_03_Problem_Definition.txt
```

The full user prompt must never be used as the subtopic filename.

Filename handling must:

-   remove invalid Windows characters
-   normalize whitespace
-   avoid reserved Windows names
-   enforce a safe filename length
-   avoid duplicate filenames
-   preserve readable titles

# 5. Repeated Subtopic Checker

## Objective

Prevent the course from containing multiple subtopics that teach
essentially the same thing.

The checker must detect:

### Exact duplicates

``` text
User Research
User Research
```

### Near duplicates

``` text
Understanding User Needs
Identifying User Needs
```

### Description-level repetition

Two different titles may still have almost identical descriptions.

### Semantic overlap

The titles/descriptions should be compared for meaningful similarity
rather than only exact string matching.

The implementation should use an approach compatible with the current
offline/local architecture and should not introduce an unnecessary
external API.

# 6. Short / Weak Subtopic Detection

A structurally valid subtopic can still be poor quality.

V4 should add quality validation for:

-   very short titles
-   excessively long titles
-   empty descriptions
-   extremely short descriptions
-   repetitive descriptions
-   duplicate/near-duplicate topics
-   meaningless generic topics
-   subtopics that do not fit the lesson
-   invalid or missing metadata

The validator should consider the existing content-length configuration
and estimated character information instead of blindly applying one
global threshold.

------------------------------------------------------------------------

# 7. Subtopic Regeneration

When a generated subtopic fails quality validation, it must be
regenerated.

Recommended flow:

``` text
Generate
   ↓
Validate
   ↓
PASS ─────────────→ Continue
   │
   FAIL
   ↓
Explain failure
   ↓
Regenerate
   ↓
Validate again
```

Use a configurable maximum number of regeneration attempts.

Example:

``` python
MAX_SUBTOPIC_REGENERATION_ATTEMPTS = 3
```

The regeneration prompt should contain the actual validation reason
where useful.

Example:

``` text
The previous subtopic was rejected because:
- the title is too long
- it overlaps with another subtopic
- the description is too repetitive

Generate a shorter, distinct subtopic focused on a different aspect of the lesson.
```

Do not allow infinite regeneration.

If the maximum number of attempts is exhausted:

``` text
status = failed
failure_reason = ...
```

The failure must remain visible in the checkpoint rather than silently
accepting poor output.

# 8. B6 --- Tasklist Not Updated for Resumed Content

## Existing Problem

When completed content is restored from an existing file/checkpoint, the
content can be recognized as completed while `tasklist.json` remains
incomplete.

This creates inconsistent state.

## V4 Requirement

When completed content is restored:

``` text
content = completed
tasklist = completed
checkpoint = completed
```

All relevant state representations must agree.

The resume process should be idempotent.

Running resume multiple times should not repeatedly modify or corrupt
state.

------------------------------------------------------------------------

# 9. B7 --- Fragile Subtopic Numbering

## Existing Problem

Subtopic numbering currently relies on lesson/list ordering.

If lessons are reordered, the generated numbering can become
inconsistent.

## V4 Requirement

Use stable identifiers for lesson/subtopic identity wherever possible.

Do not use a mutable list position as the only identity.

The system should maintain consistent:

``` text
lesson identity
subtopic identity
lesson number
subtopic number
```

even when lists are loaded, restored, reordered, or regenerated.

Example:

``` text
Lesson 1
  Subtopic 1
  Subtopic 2
  Subtopic 3

Lesson 2
  Subtopic 1
  Subtopic 2
```

The numbering should remain deterministic and tied to the correct
lesson.

------------------------------------------------------------------------

# 10. Web Search --- All Websites Trusted

## Objective

Remove unnecessary domain restrictions from the trusted website
configuration.

Normal public websites should be allowed by default.

There should not be a small hardcoded domain whitelist blocking
otherwise valid sources.

However, this does **not** mean disabling network security.

Keep:

-   HTTPS/HTTP validation
-   URL parsing
-   timeout handling
-   crawler error handling
-   content extraction checks
-   SSRF protections
-   private/local IP blocking where appropriate
-   invalid URL rejection
-   other existing security safeguards

The intended behavior is:

``` text
Normal public website
       ↓
Allowed
```

rather than:

``` text
Website
  ↓
Is it in hardcoded whitelist?
  ↓
No → reject
```

The existing web-search architecture should be preserved.

# 11. DOCX Formatting Improvement

## Problem

Generated content can contain Markdown syntax such as:

``` markdown
# Introduction

## User Research

**Important concept**

- Point one
- Point two
```

When exported to Word, these can appear as literal Markdown characters
instead of actual Word formatting.

The DOCX exporter should convert supported Markdown-style structures
into proper DOCX formatting.

### Required mappings

``` text
# Heading 1       → Word Heading 1
## Heading 2      → Word Heading 2
### Heading 3     → Word Heading 3

**bold**           → Word bold
*italic*           → Word italic

- item             → Word bullet list
1. item            → Word numbered list
```

The DOCX output should have:

-   proper heading hierarchy
-   bold emphasis
-   readable paragraph spacing
-   clean bullet/numbered lists
-   consistent alignment
-   no unnecessary raw Markdown markers

Do not break existing DOCX export functionality.

# 12. Memory-Efficient Content Persistence

Generated content should not unnecessarily accumulate in RAM.

Preferred flow:

``` text
Generate one subtopic
       ↓
Validate
       ↓
Persist result/checkpoint
       ↓
Write final output
       ↓
Release temporary references
       ↓
Generate next subtopic
```

The goal is:

-   lower unnecessary memory usage
-   better crash recovery
-   less duplicate work
-   easier resume

This should not be described as a guarantee that LLM inference itself
becomes faster. LLM inference time is primarily dependent on
model/runtime performance.

# 13. Version 4.0 --- Three Implementation Phases

# Phase 1 --- Generation & Subtopic Quality

### Objective

Make the generated course structure reliable before content/output work
proceeds.

### Work

1.  Shorten and validate subtopic names.
2.  Add repeated/near-duplicate subtopic checker.
3.  Add weak/short subtopic detection.
4.  Add subtopic regeneration.
5.  Add configurable regeneration limit.
6.  Fix subtopic identity/numbering.
7.  Ensure regenerated subtopics replace rejected versions correctly.
8.  Preserve checkpoint state through regeneration.

### Phase 1 success criteria

``` text
Subtopic Generation
       ↓
Quality Validation
       ↓
   ┌───┴───┐
   ↓       ↓
 PASS    FAIL
   ↓       ↓
Continue Regenerate
           ↓
        Validate
```

No accepted subtopic should be obviously duplicated, meaningless, or
outside the configured size/quality expectations.

------------------------------------------------------------------------

# Phase 2 --- Output, Persistence & Resume Reliability

### Objective

Make generation persistence deterministic and eliminate
duplicate/incorrect files.

### Work

1.  Remove duplicate `.txt` writing.
2.  Establish one authoritative output writer.
3.  Fix content-generation filename mismatch.
4.  Generate short Windows-safe filenames.
5.  Persist generated results promptly.
6.  Fix tasklist restoration for resumed content.
7.  Keep checkpoint/tasklist/output state synchronized.
8.  Verify interrupted runs resume correctly.
9.  Prevent duplicate output after resume.
10. Preserve quiz/question-bank generation.

### Phase 2 success criteria

For every subtopic:

``` text
One generated result
        ↓
One checkpoint state
        ↓
One final TXT file
```

A resumed completed subtopic must not generate another file.

------------------------------------------------------------------------

# Phase 3 --- Web Search & DOCX Delivery

### Objective

Improve source accessibility and make final Word documents professional.

### Work

1.  Remove unnecessary trusted-domain restrictions.
2.  Allow normal public websites by default.
3.  Preserve network/security protections.
4.  Improve Markdown-to-DOCX conversion.
5.  Convert headings to Word heading styles.
6.  Convert bold/italic syntax to actual formatting.
7.  Convert Markdown lists to Word lists.
8.  Fix spacing/alignment issues.
9.  Verify generated DOCX files visually/structurally.
10. Add regression tests for web search and DOCX export.

### Phase 3 success criteria

Web search:

``` text
Valid public website
        ↓
Allowed
        ↓
Fetched
        ↓
Extracted
        ↓
Analyzed
```

DOCX:

``` text
Markdown-like generated content
        ↓
DOCX conversion
        ↓
Real Word headings
Real bold
Real lists
Clean formatting
```

# 16. Implementation Principle

Do not rebuild the Content Generator.

Version 4 should be a **controlled stabilization and quality upgrade**
of the current architecture.

Keep the existing pipeline and improve its weak points:

``` text
Existing V3 Architecture
        ↓
V4 Phase 1
Subtopic Quality
        ↓
V4 Phase 2
Persistence + Output + Resume
        ↓
V4 Phase 3
Web Search + DOCX
        ↓
Stable V4
```

The implementation should favor small, testable changes over a large
rewrite.
